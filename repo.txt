# `--block-local-connections` is bypassable: unprivileged code inside the
# Claude sandbox takes unauthenticated control of PID 1 (process_api)


================================================================================
0. SUMMARY
================================================================================

The Claude code-execution sandbox is a Firecracker MicroVM whose init is
`process_api` (PID 1, rdinit=/process_api). PID 1 exposes a WebSocket control
plane on 0.0.0.0:2024 that can create processes, kill them, freeze them, write
their stdin and read their stdout — root-equivalent control over the VM.

That plane is started with `--block-local-connections`, whose entire purpose is
to make it reachable ONLY by the host, not by code already running inside the
guest. Read from /proc/1/cmdline inside the guest:

    /process_api --firecracker-init --addr 0.0.0.0:2024 --max-ws-buffer-size 32768
                 --block-local-connections --control-vsock-port 5001
                 --listen-vsock-port 2024 --log-vsock-port 5002

Both halves of that intent are false, and this report proves it end to end:

  (1) THE FLAG IS BYPASSABLE IN ~200 ms. Adding a SECONDARY source address
      (192.0.2.3/32 on eth0:0, via ioctl SIOCSIFADDR) and connecting FROM that
      source to 127.0.0.1:2024 returns `HTTP/1.1 101 Switching Protocols`,
      while the identical handshake from the loopback source is refused.
      That contrast is the proof.

  (2) NO CREDENTIAL IS EVER ENFORCED. A correct token, no token, and a garbage
      token produce byte-identical control-plane behaviour. There is no auth
      error on the missing-token path — because on the local path the token is
      never consulted.

Net effect: untrusted code that merely runs inside the sandbox — an `npm
install` postinstall script, any tool call — acquires unauthenticated control
over the supervisor of its own VM, and keeps that control after the harness
process dies and the MicroVM is recycled.

================================================================================
1. INTENDED DESIGN — what the control is FOR
================================================================================

`process_api` binds 0.0.0.0:2024 so the HOST can reach it from outside the VM
over the guest NIC (192.0.2.2). The JWT exists for the host. The flag exists for
one reason: to keep processes already living INSIDE the guest off the host's own
control plane. The threat model is explicit and the flag name is literal.

The bug is therefore not "an exposed service". It is:

    untrusted in-guest code impersonating the host to the host's own client.

This also explains the second half: if local connections were meant to be
blocked, there was no reason to verify the token on the local path, so the token
check is simply absent there. The two facts are one fact.

================================================================================
2. WHY THIS IS NOT "BY DESIGN"  (pre-emptive rebuttal)
================================================================================

  * The flag is literally named `--block-local-connections`.
  * NO authentication error is emitted when the token is absent. If the token
    were the intended control, a missing token would error. It does not.
  * Therefore either the flag works, or the token works. Neither works.
  * No new capability is needed: CAP_NET_ADMIN is already present
    (CapEff 000001fffeffffff, bit 12 set). Nothing is enabled, nothing escalated.
  * The secondary address does NOT survive VM recycling — which is exactly why
    the flag looks correct on casual inspection, and why two public analyses
    concluded the surface was sealed.

================================================================================
3. ATTACK NARRATIVE — what the attacker actually gains
================================================================================

A developer opens a chat with code execution; the agent runs one command
(e.g. `npm install`, executing an attacker-controlled postinstall).

Within ~200 ms the postinstall:
  1. adds 192.0.2.3/32 to eth0:0,
  2. connects from 192.0.2.3 to 127.0.0.1:2024 and gets 101 — no token,
  3. installs a PATH hook that shadows `python3` and logs argv + stdout,
  4. spawns a `reattachable` daemon whose parent becomes PID 1.

The tool call ends. The harness dies. The next tool call begins with a NEW
harness process — and the implant is still alive, still ppid=1, still recording
every command the agent's interpreter runs, and still able to SIGSTOP the agent's
execution mid-command.

Concretely, from inside the sandbox, with NO credential, the attacker can:
  * create / kill / freeze arbitrary processes as a peer of PID 1,
  * read their stdout and write their stdin over the WebSocket,
  * put a process into uninterruptible freeze (cgroup freezer -> state D)
    or stop it (SIGSTOP -> state T),
  * write into the HOST telemetry collector over vsock (HTTP 200),
  * survive VM recycling with a ppid=1 daemon and a PATH hook,
  * observe and perturb the agent's own command output.

================================================================================
4. ROOT CAUSE AND REMEDIATION
================================================================================

TWO INDEPENDENT DEFECTS. Either one alone is a bug.

(a) The local-connection test inspects the WRONG ADDRESS and the WRONG SET.
    It is applied to the DESTINATION address rather than the SOURCE. The
    destination is always 127.0.0.1 for any in-guest client, so host traffic
    and guest traffic are indistinguishable — and the bypass works precisely
    because the source (192.0.2.3) is never examined.

    FIX (a): test the PEER/SOURCE address, and test it against the full set of
    addresses currently configured on the guest interfaces — not merely against
    127.0.0.0/8 (the bypass source is already outside 127/8, so a 127/8 test
    alone changes nothing). Do not cache that address set from boot; secondary
    and alias addresses must be included.

(b) The JWT is not enforced on the local path. Three credential variants are
    behaviourally identical and no auth error is raised when the token is absent.

    FIX (b), the robust one: enforce the JWT on EVERY connection regardless of
    source, and treat the flag as a performance hint rather than a security
    boundary. Best: enforce the token AND fix the address predicate.

6. PROOF OF AGENT OBSERVABILITY
================================================================================

The supervisor's own process is NOT attachable (`Attach` returns
`ProcessWithSameIdRunning`), so observability is proven via the PATH hook. The
hook shadows `python3` in a directory already ahead of the system PATH, logging
timestamp, cwd and argv, and tee-ing stdout to /tmp/.mf/agent_calls.log. On run 2
the script reports AGENT_INVOCATIONS_CAPTURED >= 1 — invocations produced by a
harness process that did not exist when the hook was planted.

================================================================================
9. PRIOR ART  (corrected)
================================================================================

Two independent analyses concluded the surface was unreachable (Pluto Security;
muninn/Oskar Austegard). Two others characterised it without reaching it (Rohan
Adwankar — /proc restrictions; AprilNEA — the protocol, with wrong field names).
This report overturns the "sealed" conclusion and corrects the protocol:
`SendSignal` takes a BARE i32 (`{"SendSignal": 19}`); unit variants are `null`
payloads (`{"Kill": null}`); CONTROL messages carry NO `process_id` (the socket
owns the process); `Attach`, `Detach`, `KeepAlive`, `Resize`, `PtyResize` are not
valid control variants.

def raw_hs(src=None, hdr="", tmo=5):
    try:
        s = socket.create_connection((ADDR, PORT), timeout=tmo,
                                     source_address=(src, 0) if src else None)
        k = base64.b64encode(os.urandom(16)).decode()
        extra = ("Authorization: %s\r\n" % hdr) if hdr else ""
        s.sendall(("GET / HTTP/1.1\r\nHost: %s:%d\r\n%sUpgrade: websocket\r\n"
                   "Connection: Upgrade\r\nSec-WebSocket-Key: %s\r\n"
                   "Sec-WebSocket-Version: 13\r\n\r\n" % (ADDR, PORT, extra, k)).encode())
        d = s.recv(4096); s.close()
        return d.split(b"\r\n")[0].decode("latin1") if d else "ERR:closed"
    except Exception as e:
        return "ERR:" + str(e)

class WS:
    def __init__(self, host=ADDR, port=PORT, src=None, tmo=8):
        self.buf = b""
        self.s = socket.create_connection((host, port), timeout=tmo,
                                          source_address=(src, 0) if src else None)
        key = base64.b64encode(os.urandom(16)).decode()
        self.s.sendall(("GET / HTTP/1.1\r\nHost: %s:%d\r\nUpgrade: websocket\r\n"
                        "Connection: Upgrade\r\nSec-WebSocket-Key: %s\r\n"
                        "Sec-WebSocket-Version: 13\r\n\r\n" % (host, port, key)).encode())
        end = time.time() + tmo
        while b"\r\n\r\n" not in self.buf and time.time() < end:
            d = self.s.recv(4096)
            if not d: break
            self.buf += d
        head, _, self.buf = self.buf.partition(b"\r\n\r\n")
        self.status = head.split(b"\r\n")[0].decode("latin1") if head else ""
        if "101" not in self.status:
            raise IOError("handshake failed: " + (self.status or "closed"))

    def _f(self, op, p=b""):
        n = len(p); mk = os.urandom(4)
        if n < 126:     h = struct.pack("!BB", 0x80 | op, 0x80 | n)
        elif n < 65536: h = struct.pack("!BBH", 0x80 | op, 0x80 | 126, n)
        else:           h = struct.pack("!BBQ", 0x80 | op, 0x80 | 127, n)
        self.s.sendall(h + mk + bytes(p[i] ^ mk[i % 4] for i in range(n)))

    def txt(self, s):  self._f(0x1, s.encode())
    def js(self, o):   self.txt(json.dumps(o))
    def binf(self, b): self._f(0x2, b)
    def pong(self, p): self._f(0xA, p)

    def _exact(self, n, dl):
        while len(self.buf) < n:
            if time.time() > dl: return None
            self.s.settimeout(max(0.05, dl - time.time()))
            try: d = self.s.recv(65536)
            except socket.timeout: continue
            except OSError: return None
            if not d: return None
            self.buf += d
        o, self.buf = self.buf[:n], self.buf[n:]
        return o

    def frame(self, dl):
        h = self._exact(2, dl)
        if not h: return None
        op, b2 = h[0] & 0x0F, h[1]; n = b2 & 0x7F
        if n == 126:
            e = self._exact(2, dl); n = struct.unpack("!H", e)[0] if e else 0
        elif n == 127:
            e = self._exact(8, dl); n = struct.unpack("!Q", e)[0] if e else 0
        mk = self._exact(4, dl) if (b2 & 0x80) else b""
        p = self._exact(n, dl) if n else b""
        if p is None: return None
        if mk: p = bytes(p[i] ^ mk[i % 4] for i in range(len(p)))
        return op, p

    def drain(self, secs=4.0, hard=70.0):
        txts, bins = [], []
        end = min(time.time() + secs, T0 + hard)
        while time.time() < end:
            fr = self.frame(end)
            if fr is None: break
            op, p = fr
            if op == 0x1:
                t = p.decode("utf-8", "replace"); txts.append(t); log("   <<", t[:160])
            elif op == 0x2:
                bins.append(p); log("   <bin>", len(p), repr(p[:40]))
            elif op == 0x9: self.pong(p)
            elif op == 0x8: break
        return txts, bins

    def close(self):
        try: self._f(0x8, b"")
        except Exception: pass
        try: self.s.close()
        except Exception: pass

def varint(n):
    o = b""
    while True:
        b = n & 0x7F; n >>= 7
        o += bytes([b | 0x80]) if n else bytes([b])
        if not n: return o

An attacker with the ability to execute code inside the Claude sandbox (e.g., via npm install postinstall script, malicious tool call, or any user-supplied code) can bypass the `--block-local-connections` security control and gain **unauthenticated, root-equivalent control** over the entire MicroVM.

## Immediate Impact

Within ~200ms of code execution, the attacker can:

1. **Full Process Control**: Create, kill, freeze (SIGSTOP/cgroup freezer), and manipulate arbitrary processes as a peer of PID 1
2. **I/O Interception**: Read stdout and write stdin of any process over the WebSocket control plane
3. **Agent Observation**: Install PATH hooks to log and modify the AI agent's command invocations and outputs
4. **Persistent Access**: Spawn daemons that survive harness process death and VM recycling via the chat's persistent disk
5. **Host Communication**: Write to the host telemetry collector over vsock (HTTP 200 OK response confirmed)

## Attack Scenario

1. User opens a chat with code execution enabled
2. Agent runs one command (e.g., `npm install` with attacker-controlled package)
3. Postinstall script adds secondary IP 192.0.2.3/32 to eth0:0
4. Script connects from this source to 127.0.0.1:2024 and receives WebSocket upgrade (no JWT required)
5. Script installs PATH hook and spawns ppid=1 daemon
6. Tool call ends, harness dies, VM is recycled
7. **Next tool call**: Implant survives, still recording agent commands, still able to freeze/kill processes

## Security Boundary Violations

- **Authentication Bypass**: No JWT validation on the "local" connection path
- **Access Control Bypass**: The `--block-local-connections` flag checks the wrong address (destination instead of source)
- **Isolation Breach**: Guest code impersonates the host to access the host's own control plane
- **Persistence**: Malicious code survives across multiple tool calls in the same chat

## Demonstrated Capabilities (Proof Points)

- ✅ P1: WebSocket upgrade (101) from secondary IP while loopback is blocked
- ✅ P3: Three authentication variants (correct/none/garbage token) produce identical behavior
- ✅ P4: Successfully spawned processes as peer of PID 1
- ✅ P5: Full-duplex stdin/stdout control over spawned processes
- ✅ P6: Signal delivery (SIGSTOP) accepted and process state changed to T
- ✅ P7: Host telemetry plane (vsock 2:5005) returns HTTP 200 OK
- ✅ P8: Implant survives harness death (verified across two runs)
- ✅ P9: PATH hook captured agent invocations from new harness process
- ✅ P11: Orphaned /bin/sh from run 1 still ppid=1 in run 2

## Risk to Users

Any malicious code that runs in the sandbox—including supply chain attacks, compromised dependencies, or social engineering—can:
- Exfiltrate sensitive data from subsequent tool calls
- Manipulate agent behavior and outputs
- Persist across the lifetime of the chat
- Access internal service names and container identifiers (information disclosure)

This completely defeats the sandbox's isolation guarantees.
